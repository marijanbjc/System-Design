# ML / LLM в системе

Какие задачи решаем моделями, а какие — правилами; как обучаем и валидируем эмбеддер и головы
классификации/риска; откуда берём данные и как их размечаем; какие метрики и пороги; как храним,
версионируем и переобучаем модели. Архитектурный контекст — [architecture.md](architecture.md).

## 1. Карта задач: где правила, где классика, где эмбеддинги, где LLM

| Задача | Подход | Почему так, а не иначе |
|---|---|---|
| Нормализация текста | правила / regex | детерминированно, дёшево, на горячем пути; LLM тут избыточен |
| Базовая критичность/токсичность (предфильтр) | правила + словари стоп-слов | быстрый грубый барьер ≤ мс на горячем пути |
| Обезличивание PII | локальная NER (Natasha) + regex | **нельзя** слать PII во внешнюю LLM; локально — быстрее и контролируемо |
| Классификация темы | классическая ML-голова над эмбеддингом | ≤500 мс, интерпретируемо, калибруемо, дёшево; LLM здесь дорог и неконтролируем |
| Оценка риска | вторая ML-голова над эмбеддингом | риск ортогонален теме; нужен быстрый скор на горячем пути |
| Поиск типовых / поиск по базе знаний | эмбеддинги + векторный поиск | семантическое сопоставление; ядро дефлекшена и RAG |
| Генерация ответа на нетиповые вопросы | LLM | единственное место, где нужна свободная генерация по контексту |
| **Где LLM НЕ используем** | классификация/маршрутизация, обезличивание, детекция всплеска, гарантии безопасности | дорого/медленно/неконтролируемо; PII-риск; для гарантий нужен детерминизм |

Общий принцип: **LLM — только на «медленном» пути генерации нетиповых обращений**; всё, что на горячем
пути и всё, что должно давать гарантии, — локальные модели и детерминированные правила.

## 2. Предобработка (до моделей)

1. **Нормализация (правила).** Срезаем HTML-разметку, подписи, цитаты предыдущих писем, служебные
   email-артефакты; приводим кодировку; обрезаем предельную длину. Одинаково для всех каналов — так
   разнородный вход приводится к единому виду без суммаризации и без LLM.
2. **Базовая критичность/токсичность (предфильтр безопасности).** Regex + словари: стоп-слова (угрозы,
   оскорбления), паттерны запрещённых тем (политика и т.п.), маркеры повышенного риска (упоминание суда,
   чарджбэка, «взлом аккаунта»). Даёт быстрый флаг `unsafe` на горячем пути. Барьер **грубый, но
   терминальный**: срабатывание уводит обращение сразу к оператору, LLM не вызывается — то есть
   safety-флаги модели этот вердикт уже не уточняют. Цена ложного срабатывания — лишний тикет у
   оператора, и это дешевле пропущенного небезопасного авто-ответа.
3. **Обезличивание PII (обратимо).** Natasha (NER: имена, локации, организации, даты) + regex (телефоны,
   email, номера карт/заказов) → замена на плейсхолдеры `[NAME_1]`, `[ORDER_1]` с сохранением пар в
   локальном волте; после ответа LLM значения восстанавливаются. Внутренние модели работают с сырым
   текстом — обезличивание нужно только перед выходом за наш контур.

## 3. Эмбеддер: контрастивное обучение (ядро)

> **Целевая картина.** Всё, что описано в этом разделе, относится к целевой системе.
> В PoC энкодер — мок на хешах, классификатор — правила по ключевым словам (§8).

**Задача.** Обучить энкодер так, чтобы обращения **одной темы** имели высокую косинусную близость, а
**разных тем** — низкую. Один и тот же эмбеддинг затем используют и головы классификации, и векторный
поиск (эмбеддим обращение один раз).

**База.** Берём открытую предобученную многоязычную модель (напр. семейства `e5 / LaBSE / ruBERT`-based
sentence-encoder) и **дообучаем** под наш домен. Обучать с нуля незачем: данных недостаточно, дообучение
дешевле и качественнее. Модель **локальная** (эмбеддим тексты с PII — внешний embedding-API избыточен).

**Функция потерь — InfoNCE**, K негативов и 1 позитив на якорь:

```
             exp( cos(a, p) / T )
L = -log ------------------------------------
         exp( cos(a, p)/T ) + Σ_i exp( cos(a, n_i)/T )
```

- `a` — якорь (обращение), `p` — позитив (см. градацию ниже), `n_i` — K негативов (обращения **других**
  тем); `T` — температура.
- Негативы: in-batch (другие примеры батча) + **hard negatives** (лексически похожие, но из другой темы) —
  они дают самый полезный сигнал.
- На выходе mean-pooling + L2-нормализация (чтобы косинус был корректной мерой).

**Градация позитивов: hard / soft.** Позитивы к якорю делим на два уровня по сходству **ответа оператора**
(answer-IoU на нормализованных ответах — см. §6):
- **hard-positive** — та же тема **и** практически тот же ответ оператора (answer-IoU ≥ порога);
- **soft-positive** — та же тема, но **другой** ответ оператора (answer-IoU < порога).

Учим не бинарно «позитив/негатив», а по порядку близости `cos(a, hard) > cos(a, soft) > cos(a, neg)`.
Реализуемо взвешенным multi-positive InfoNCE (hard — основной позитив, soft — с меньшим весом) либо
добавлением margin-ranking-члена (`cos(a,hard) − cos(a,soft) ≥ m₁`, `cos(a,soft) − cos(a,neg) ≥ m₂`).
Зачем: для дефлекшена (Tier 1) ближайший сосед должен нести **применимый** ответ, а не просто верную тему;
градация подтягивает наверх кейсы с подходящими ответами операторов.

## 4. Две головы: тема и риск

Поверх энкодера — две лёгкие головы (linear / небольшой MLP над эмбеддингом):

- **Голова темы** — многоклассовая (в целевой ~100 тем, в PoC 6–8 на синтетике), softmax +
  cross-entropy. Отдаёт `topic` и `conf_cls` (калиброванную уверенность).
- **Голова риска** — отдельная (риск ортогонален теме: в одной теме бывают и рисковые, и безобидные
  обращения). Отдаёт **не бинарную метку, а скор `conf_risk ∈ [0,1]`**, который сравнивается с
  порогом и превращается в `risk ∈ {low, medium, high}`. Скор удобнее метки: пороги настраиваются без
  переобучения, и мы всегда можем сдвинуть их в сторону осторожности.

**Схема обучения (поэтапно, для стабильности):** сначала контрастивно обучаем энкодер (§3), затем
фиксируем его и обучаем головы; опционально — совместное дообучение (multi-task: InfoNCE + две CE).
Почему головы над общим эмбеддингом, а не отдельные модели: экономим один forward на горячем пути и
держим представление согласованным.

## 5. Ретрив: индексы троек и базы знаний

- **Индекс троек** `(обращение, класс, ответ)` — эмбеддинги обращений; поиск с **фильтром по теме**
  (сначала классификатор сузил тему → ищем только внутри неё → выше точность). `best_sim ≥ TAU_HIGH` в
  теме `AUTO_OK` = типовой (Tier 1).
- **Индекс базы знаний** — статьи от менеджеров, **обогащённые вероятными вопросами гостя** (генерация
  вопроса офлайн-LLM, если менеджер не приложил свой): пользователь задаёт вопрос, а в статье —
  декларативный текст; вопрос-представление перекидывает мостик и поднимает recall.
  **В вектор попадает только вопрос**, текст статьи хранится рядом и отдаётся как контекст —
  эмбеддинг вопроса к вопросу совпадает заметно лучше, чем вопрос к справочному тексту.

## 6. Данные и разметка

- **Источник** — исторические тикеты: обращение, тема, риск, ответ оператора, исход (reopen / эскалация /
  CSAT).
- **Метки темы** — операторы уже проставляют категории → используем как разметку.
- **Метки риска** — операторы заполняют риск по историческим обращениям (подтверждено вводными задания);
  плюс слабые сигналы (reopen, эскалация, жалоба, низкий CSAT) как уточняющие/дополнительные метки.
- **Тройки для индекса типовых** — из истории: группируем обращения по типовым тикетам операторов, берём
  частотные, формируем `(обращение, класс, ответ)`; либо менеджер добавляет вручную (ручка `/kb/triples`).
- **Дисбаланс** — темы редкие/частые: взвешивание классов, oversampling редких, hard-negative mining.
- **Гигиена** — дедупликация, отсев противоречивых меток, обезличивание обучающих текстов.
- **Шаблонные ответы операторов → нормализация перед обучением.** Операторы часто шлют «заготовку», в
  которой меняются лишь переменные слоты (имя гостя, номер заказа, телефон курьера, статус заказа). Такие
  слоты **маскируем** (той же логикой обезличивания: `[NAME]`, `[ORDER]`, `[STATUS]`…) в ответах оператора
  **до** обучения и **до** расчёта answer-IoU для градации позитивов (§3). Иначе два одинаковых по сути
  ответа, отличающихся одним словом (именем клиента), модель сочла бы разными — и мы бы ошибочно занижали
  их близость.

## 7. Валидация и метрики

**Сплит — по времени, а не случайно.** Train — прошлое, valid/test — самый свежий период. Случайный сплит
даёт утечку (почти дубли обращений попадут и в train, и в test) и завышает метрики. Индексы троек/БЗ для
оценки строим только по данным **до** отсечки — иначе утечка в ретрив.

| Компонент | Метрики | На что смотрим особенно |
|---|---|---|
| Эмбеддер (ретрив) | Recall@k, MRR | находим ли верного кандидата для типовых |
| Голова темы | macro-F1, per-class precision/recall, confusion matrix | recall на **рисковых** темах (пропуск дороже ошибки) |
| Голова риска | PR-AUC, recall на класс «рисковый» | высокий recall риска (лучше лишний раз к оператору) |
| Калибровка | ECE, reliability curve | уверенность должна быть осмысленной — на ней стоят пороги |
| Генерация (офлайн) | обоснованность, корректность, доля отказов | сверка с эталонными ответами операторов (выборка / LLM-judge) |

Обоснованность в последней строке — **офлайн-метрика на выборке**, а не рантайм-гейт: в проде мы её не
считаем (см. §9 и упрощения в architecture.md).

**Выбор порогов.** `TAU_HIGH` (Tier 1) и `TAU_CONF` (авто-отправка генерации) подбираем по held-out по
кривой precision/recall: держим **высокую точность** авто-ответов (мало неверных авто-ответов) при
приемлемой доле автоматизации. Приоритет — не уронить CSAT/reopen (см. [monitoring.md](monitoring.md)).

## 8. Baseline первым, потом апгрейд

| | Baseline (первым)                                                                | Апгрейд |
|---|----------------------------------------------------------------------------------|---|
| Классификация | заморож. открытый энкодер (или TF-IDF-фичи) + случайная линейная голова (LogReg) | дообучаем и энкодер контрастивно (§3), и голову |
| Ретрив | открытый многоязычный энкодер без дообучения + косинус                           | дообученный энкодер (§3) |
| Риск | правила (стоп-слова + категории)                                                 | ML-голова риска |

Важно: классификация в любом случае требует размеченных данных — «baseline» означает не «без обучения», а
что мы **не трогаем энкодер** (берём готовый/заморожённый или простые TF-IDF-фичи) и обучаем только лёгкую
голову на наших метках; апгрейд — это уже дообучение самого энкодера. Дообучение энкодера оправдано,
**только если бьёт baseline** на тех же метриках — иначе оставляем простое решение.

**PoC не доходит даже до левой колонки:** и энкодер, и классификатор в нём — моки (хеши и правила по ключевым словам). Обучать модель на выдуманном датасете внутри прототипа избыточно — он показывает работоспособность маршрутизации, а не качество классификации. Baseline из левой колонки — первый шаг на реальных исторических данных.

## 9. Обработка низкой уверенности (abstain-to-human)

Неуверенность на любом этапе → человек, а не угадывание:
- `conf_cls` низкая → не доверяем теме → безопасный дефолт (`REVIEW_REQUIRED` / оператор);
- `best_sim < TAU_HIGH` → не типовой → генерация;
- `conf_gen < TAU_CONF` → оператор;
- `has_enough_context < TAU_CTX` → оператор. Модель возвращает достаточность контекста **скором
  `[0,1]`, а не булевым флагом**: порог тогда наш и настраивается без смены промпта. Это самооценка
  модели, а не наша проверка заземлённости — ограничение осознанное, чем заменяется в целевой картине
  см. в architecture.md §12.

## 10. Хранение, версионирование, переобучение

**Хранение и версии.**
- *Целевая:* **MLflow** — трекинг экспериментов + Model Registry (версии, метрики, стадии
  staging/production). Воркеры тянут модель по версии; версия пишется в аудит тикета
  (`classifier_version`, `encoder_version`) → любое решение воспроизводимо.
- *PoC (предложение):* без поднятия сервера — модели как файлы в `models/` + манифест
  `models/registry.json` (имя, версия, дата обучения, метрики, путь). Загружаем по версии на старте,
  версию пишем в аудит. Это минимальная реализация той же идеи, что и Registry; при желании показать
  процесс — локальный MLflow с file-backend (`mlruns/`). В PoC модели мок/крошечные, поэтому версия
  фактически зашита.

**Периодичность переобучения.**
- *Целевая:* индексы троек/БЗ обновляем часто (ежедневно / по мере поступления — это дёшево); энкодер и
  головы переобучаем по расписанию (напр. раз в 2–4 недели) **и по триггеру** — при просадке метрик или
  дрейфе распределения (см. [monitoring.md](monitoring.md)). Новая тема → добавляем класс и дообучаем голову.
- *PoC:* не переобучаем (моки) — описываем процесс и оставляем точки расширения.
