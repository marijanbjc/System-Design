# Автоматизация обработки тикетов поддержки — дизайн + PoC

Система принимает обращения из разных каналов (email, чат, веб-форма, мобильное приложение),
классифицирует их локально за миллисекунды и либо отвечает сама, либо передаёт оператору.
Ответ на типовой вопрос отдаётся синхронно из индекса предодобренных ответов, нетиповой —
асинхронно генерируется по базе знаний, рискованный не закрывается автоматически никогда.

## Зачем это бизнесу

Поддержка обрабатывает ~200k тикетов в день по 150 ₽ за тикет, при этом около 40% потока —
повторяющиеся типовые вопросы, на которые оператор пишет один и тот же ответ. Система снимает
эту часть нагрузки, отвечая мгновенно и без участия человека, а во время массовых сбоев гасит
всплеск одним заготовленным сообщением вместо тысяч ручных ответов. Операторы при этом
получают не меньше работы, а другую: сложные и рискованные обращения приходят к ним с готовым
черновиком и подобранным контекстом. Ключевое ограничение осознанное — автоматизация не имеет
права ухудшить CSAT и reopen rate, поэтому всё неуверенное и рискованное уходит человеку, а не
закрывается ради красивой цифры дефлекшена.

## Быстрый старт

```bash
make install && make demo
```

`make install` создаёт venv и ставит проект из `pyproject.toml` как editable-пакет,
`make demo` поднимает Redis Stack в docker, наполняет индексы и прогоняет все сценарии
end-to-end. API-ключ не нужен: LLM — детерминированный мок.

```bash
make test    # 63 теста, включая проверку, что ПДН не уходят во внешний вызов
make lint    # ruff: линт и проверка форматирования
make run     # поднять API на http://localhost:8000 (Swagger на /docs)
```

## Что демонстрирует демо-скрипт

| Сценарий | Ожидаемый исход |
|---|---|
| Типовой вопрос про возврат | `200`, `tier1_auto` — готовый ответ из индекса троек, без LLM и без оператора |
| Нетиповой вопрос с ПДН | `202` → воркер → `tier2_auto`: во внешний вызов ушли `[PHONE_1]`/`[ORDER_1]`, значения восстановлены после ответа |
| Вопрос без контекста в базе знаний | гейт не пропускает авто-отправку → оператору |
| Платёжный спор | `tier3_operator`, LLM не вызывается вообще |
| Prompt injection в тексте | `tier3_operator`, флаг `injection_suspected` в аудите |
| Токсичное обращение | `tier3_operator`, предфильтр терминален |
| LLM недоступна | деградация в оператора, событие `Generated.failed` в аудите |
| Всплеск по теме «оплата» | `answered_surge` — заготовленный менеджером ответ, без LLM |
| Менеджер добавил тройку | тот же вопрос сразу отвечается через `tier1_auto` |
| Статья БЗ без вопроса | вопрос гостя генерируется офлайн при индексации |
| Ревью оператором | очередь с причиной эскалации; `draft_text` и `answer_text` хранятся отдельно |

Маршрут любого тикета целиком виден в `GET /tickets/{id}/audit`.

## Что здесь реальная реализация, а что дизайн

**Работает в коде:** приём из любого канала, нормализация правилами, regex-детекторы инъекций и
токсичности, локальный эмбеддинг, классификатор темы и риска, векторный поиск в
Redis Stack с фильтром по теме, детекция всплеска на минутных бакетах, детерминированная политика
автоматизации, обратимое обезличивание ПДН, три очереди на Redis Streams, token-bucket rate limiter
на Lua, воркер генерации с пре-гейтом и гейтом, воркер доставки, очередь и ревью оператора,
append-only аудит в SQLite.

**Осталось дизайном:** реальный провайдер LLM (в PoC только детерминированный мок), исходящие
адаптеры каналов (воркер доставки пишет в лог), парсер вики и чанкер (менеджер присылает готовый
текст статьи), джоба автопополнения индекса троек, бюджетный предохранитель по токенам,
вытеснение задач по дедлайну.


## Структура

Каждый пакет — одна зона ответственности, зависимости идут строго сверху вниз:
`api → routing → {preprocessing, ml, storage, queues}`, а `workers` дополнительно
зависит от `llm`. Обратных связей нет.

```
app/
  main.py              точка входа: uvicorn app.main:app
  config.py            все пороги и магические числа, больше нигде
  models.py            контракт API, запись тикета, схема выхода LLM

  api/                 HTTP-поверхность
    routes.py            приём, статус, аудит, ревью, админ-ручки
    schemas.py           тела запросов админ-ручек
    deps.py              сборка зависимостей — видно, что от чего зависит

  preprocessing/       предобработка обращения
    normalizer.py        очистка правилами: HTML, подписи, цитаты
    detectors.py         regex-детекторы prompt injection и токсичности
    pii.py               обратимое обезличивание персональных данных

  ml/                  эмбеддинги и классификация
    encoder.py           локальный энкодер (в PoC — детерминированный мок)
    classifier.py        классификатор темы и риска (в PoC — правила по словам)

  routing/             маршрутизация
    router.py            горячий путь ≤500 мс, без внешних вызовов
    gates.py             пре-гейт и гейт вокруг генерации

  llm/                 работа с языковой моделью
    mock.py              системный промпт, сборка контекста, детерминированный мок

  queues/              очереди и ограничение нагрузки
    streams.py           Redis Streams: генерация, ревью, доставка
    limiter.py           token bucket на Lua перед каждым вызовом LLM

  storage/             хранилища
    vector_index.py      векторные индексы троек и базы знаний (redisvl)
    state.py             счётчики всплеска, политика, заглушки, волт ПДН
    audit.py             append-only аудит и тикеты (SQLite)

  workers/
    generation.py        асинхронная генерация: пре-гейт → скрабинг → LLM → гейт
    delivery.py          доставка ответа в канал (в PoC — лог)
    kb_indexer.py        офлайн-индексация статей: вопрос гостя → вектор

data/                  23 предодобренных тройки, 16 статей базы знаний
scripts/               seed.py — наполнение индексов, demo.py — сквозные сценарии
tests/                 предобработка, маршрутизация, гейты, утечка ПДН, админ-ручки
```
